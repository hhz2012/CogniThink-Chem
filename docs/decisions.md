## D1 实现语言与技术栈（已定）

- **结论**：C# / .NET 8。
- **理由**：类型系统适合表达"规则/命题/依据链"这类强约束领域模型；`System.Text.Json` 可零依赖完成声明式数据加载；`dotnet test` 便于建立规则回归；与用户既有技术栈一致，降低维护成本。
- **被否决的选项**：Python（化学生态好，但与既有 C# 栈割裂）；TypeScript（前后端统一，但规则引擎与数值校验表达力较弱）。
- **落地约定**：
  - 目标框架 `net8.0`，`Nullable` 开启，隐式 using 开启。
  - 解决方案结构：`src/CogniThink.Chem.Core`（领域与引擎）、`src/CogniThink.Chem.Cli`（演示/自检入口）、`tests/CogniThink.Chem.Tests`（xUnit）。
  - 数据资产放 `data/`，统一 JSON；枚举以字符串序列化，字段 camelCase，兼容大小写与注释。
  - 不引入第三方 NuGet 运行时依赖；测试框架除外（xUnit）。
  - 命名：项目名 `CogniThink.Chem.*`；命名空间同名；数据 id 采用 `KH-`（知识点）、`RED-/SOL-/EQ-/EXPT-/STR-...`（规则）、`T-`（回归用例）前缀。

## D2 LLM 提供方与部署形态（建议采纳，待确认）

- **推荐**：云端 API 起步 + `ILlmClient` 抽象；本地/私有化作为可替换实现。
- **理由**：
  1. 项目核心难点在规则与推理的确定性，LLM 只承担语言层，云端 API 足以验证价值，无需先投入算力基础设施。
  2. 抽象成接口后，切换本地模型只影响一个实现类，不牵动推理层。
  3. 必须保留"规则解析兜底"：无 LLM 或无网络时，题目结构化退化为规则/模板解析，系统仍可运行（能力降级但可用）。
- **对备选方向的影响**：
  - 若选定本地部署：需增加模型体积/显存要求、启动时延与离线更新机制；解析质量评估集（T3-3）需在两种形态上分别跑。
  - 若完全不用 LLM：题目结构化需长期维护词表与正则，复杂题干（工艺流程、实验探究）解析能力受限；交互话术需全部模板化。
- **与合规的关系**：云端调用意味着题干文本出网，需与 D6 一并确认；未确认前，实现层默认"可关闭 LLM"。

## D3 教材版本与学段边界（建议采纳，待确认）

- **推荐**：人教版（2019）必修第一册/第二册 + 选择性必修 1/2/3；只做高中；不把初中内容纳入规则库，仅在解释中作为前置提示。
- **理由**：
  1. 与规划中的覆盖清单天然对齐，迁移成本最低。
  2. 高中边界清晰，避免"初中衔接算不算主干"的持续争议。
  3. 主干/延伸的划分以高考必考为准，书末的"拓展视野"类内容统一标延伸。
- **对备选方向的影响**：
  - 若改用苏教版/沪教版：需建立"版本差异表"（表述差异、章节顺序差异、收录范围差异），覆盖清单增加 `textbookRef` 的多版本字段，题库需按版本标注。
  - 若纳入初中衔接：需新增一层知识条目与规则（约 30–50 条），并重新界定"主干"分母。
- **当前实现状态**：`data/knowledge/knowledge.json` 已按此基线标注，文件头注明"临时基线，待确认"。

## D4 题库来源与授权（建议采纳，待确认；授权结论不代用户下）

- **推荐做法（不是授权结论）**：起步只入库自建题；外部来源一律先登记 license，仅用于内部评测，未获授权不对外发布。
- **可选来源类别、风险与需要确认的范围**：

| 类别 | 可用性 | 主要风险 | 需要用户确认的问题 |
| --- | --- | --- | --- |
| 自建题（教师命题 / 规则生成后人工审） | 高 | 质量与命题成本 | 是否有命题人力；是否接受"生成题必须人工签核" |
| 教材例题与习题 | 中 | 教材内容的复制与传播边界 | 是否有出版方授权渠道；是否仅限内部使用 |
| 高考真题 | 中 | 试题版权归属与商业使用范围需核实 | 产品是否商用；是否接受"仅内部评测" |
| 省市模拟题 | 低 | 来源分散、逐份授权成本高 | 是否愿意逐份取得授权，或直接放弃该类 |
| 开源题库 / 公开数据集 | 中 | LICENSE 兼容性（如 NC/ND 限制） | 是否允许仅非商用；能否接受 CC-BY 类署名要求 |

- **对备选方向的影响**：
  - 若产品定位为公开发布/商用：外部题基本不可直接用，题库规模将主要取决于自建产能，题库里程碑（≥100 题）需相应调整。
  - 若仅内部教研使用：可引入外部题做回归评测，但仍需在数据中标明来源与用途。
- **实现侧的既定约束（与授权无关）**：题库 schema 强制 `source.origin`、`source.license` 字段；无 license 的题目不得入库；校验器对缺失来源报错。

## D5 交互形态（建议采纳，待确认）

- **推荐**："分步卡片 + 推理 DAG 视图"为主形态；Web 优先、移动端自适应；对话仅作为辅助入口（提问/追问），不作为主界面。
- **理由**：
  1. 分级提示（L1–L4）本质是"步骤流"，卡片天然适配，且能严格限制每步信息量，避免越权给答案。
  2. 推理 DAG、能量阶梯、水合示意等需要固定版式，对话流难以承载。
  3. 纯画布推演实现成本高，且对高中生输入门槛过高。
- **对备选方向的影响**：
  - 若选纯对话：需额外的"防越权"话术约束与更细的状态机；DAG 只能降级为文字步骤，可解释性受损。
  - 若选画布：需新增画布编辑器、图元交互与撤销栈，M11 工作量显著上升。
- **当前实现策略**：只做与形态无关的服务层与视图模型（`ViewModels`），不绑定前端框架；卡片/画布都消费同一份视图模型。
